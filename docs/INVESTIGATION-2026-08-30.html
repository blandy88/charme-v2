Unauthenticated endpoint returns the admin's name and email Critical Verified live

GET /api/dev/debug-user/1 requires no token and returns real user records.

curl http://localhost:3000/api/dev/debug-user/1 → 200 {"success":true,"user":{"id":1,"name":"Cherif Med","email":"cherifmed1200@gmail.com",...}}

These three routes are registered only when NODE_ENV === "development" (server.js:3330), so Render (NODE_ENV=production) does not expose them. But they are live in any dev environment, and /api/dev/reset-rate-limit wipes the login rate limiter. server.js:3331-3440.

Fix: delete the /api/dev/* block, or gate it behind requireAdmin as well as NODE_ENV.

The entire catalogue hotlinks a third-party CDN High Verified live

All 186 product bottle images are loaded directly from Fragrantica's image host (fimgs.net/mdimg/perfume/…). Zero product images are hosted locally. All 12 spot-checked URLs return 200 today, so nothing is broken yet.

This is a structural dependency: if Fragrantica adds hotlink protection, rate-limits by referrer, or reorganises URLs, all 186 product images break at once with no fallback. It also carries copyright exposure for a commercial storefront.

Fix: download and self-host the images (or license them), keep the local images/ copies as onerror fallback.

2. Security

Any registered account can download all 503 loyalty customers Critical

GET /api/search/loyalty-profiles is protected by authenticateToken only — no requireAdmin — and returns name, phone, email, card number and points.

Verified: server.js:2919 — app.get("/api/search/loyalty-profiles", authenticateToken, async (req,res)=>{. The query is a wildcard LIKE '%q%' over four columns and q only needs two characters, so an attacker iterates 2–3 character prefixes to walk the entire customer file.

Amplifier: render.yaml:16 sets ALLOW_UNVERIFIED_LOGIN=true, so "registered" means anyone with a throwaway email. This is a real personal-data exposure.

Fix: add requireAdmin. Re-evaluate the unverified-login flag.

Admin credentials hardcoded in a tracked file, replayed on every deploy Critical

scripts/init-database.js:1938-1939:
const adminEmail = (process.env.ADMIN_EMAIL || 'cherifmed1200@gmail.com')…
const adminPassword = process.env.ADMIN_PASSWORD || 'medmedmed88';

Confirmed tracked by git. render.yaml:8 runs startCommand: npm run init-db && npm start, so this executes on every deploy and cold start. If the env vars are unset, that account is created or promoted to admin.

Fix: remove both fallbacks; fail loudly if unset. Rotate the password — it is also present in plain text in .env:18.

Rate limiting is effectively global, not per-client High

No app.set('trust proxy', …) anywhere (0 matches in server.js / db.js). Behind Render's load balancer every request appears to come from one address, so the auth limiter is 20 failed logins per 15 minutes for the entire site — one attacker locks out all customers.

Fix: app.set('trust proxy', 1) before the limiters, then re-tune.

Boot-time migration can silently DROP the loyalty tables High

server.js:369-378 — if loyalty_cards is missing a holder_name column, the app runs DROP TABLE IF EXISTS loyalty_transactions then DROP TABLE IF EXISTS loyalty_cards and recreates both. That deletes 503 customer cards and 152 transactions, on process start, with no confirmation and no backup.

Other confirmed issues

  • Reviewer emails leak publicly. /api/reviews/:fragrance and /api/reviews/:id/replies are unauthenticated and use SELECT r.*, which returns the user_email column. server.js:3455, 4076.
  • IDOR on profile read. POST /api/user/profile-details takes userId from the request body with no ownership check. server.js:1425.
  • Admin map exposed. /api/search/users and /api/stats/users need only authenticateToken; the former returns is_admin for every match. server.js:1986, 2072.
  • Weak JWT secret guard. server.js:36-53 rejects only two placeholder patterns; the current .env value dev_test_secret_change_me_… passes every check.
  • DB TLS verification disabled. db.js:208 ssl:{rejectUnauthorized:false}.
  • News cta_url unsanitised and assigned to href client-side — a javascript: URL executes on click. server.js:3025-3057.
  • No SIGTERM handler — Render sends SIGTERM on deploy, so the Postgres pool never closes cleanly. server.js:4476.

Security that is genuinely done well Verified clean

  • No SQL injection. Every user value is bound. The only dynamic SQL (server.js:2649, 2857) interpolates server-controlled literals.
  • Passwords correct. bcryptjs cost 12; both stored hashes are $2…, 60 chars. No plaintext, no SHA/MD5. Login returns an identical 401 for unknown user and wrong password — no enumeration.
  • No secrets in git history. All 153 commits searched: .env, login.json, reg.json never committed; the Neon password never appears.
  • Admin routes covered. All 16 /api/admin/* routes carry authenticateToken + requireAdmin, and requireAdmin re-reads is_admin from the DB per request.
  • Uploads and static serving are tight. multer memory storage, 5 MB cap, mimetype filter, sharp re-encode, server-generated filenames; root static files resolve through a prebuilt allowlist Map, so no path traversal.
  • Errors don't leak. Stack traces are logged server-side; clients get a generic message. DOMPurify sanitises reviews, replies, notes and store-hours strings.

The 117 per-perfume CSS files are one template emitted 117 times High

Each file is ~18 KB of rules like .40knots-theme .product-name{color:rgba(255,255,255,.95)!important}, differing only in the prefix and 2–4 accent colours. Normalised diffing shows ~90% identical content. All 117 ship and the 2.19 MB concatenation ships. Realistic collapse: 2.19 MB → ~50 KB plus one accent-variable block per perfume.

Two perfumes have silently broken theme CSS High

  • 40 Knots — entirely dead stylesheet. css/40knots-profile.css:10 declares .40knots-main-container. A CSS class selector cannot begin with a digit, so the parser discards the rule. All 100+ selectors in the 18 KB file are invalid — the whole theme does nothing. Verified in the file.
  • 1 Million Night — double-broken. The markup uses class="1millionnight-…" (also digit-leading → invalid) while the generated file is css/onemillionnight-profile.css defining .onemillionnight-theme. Neither prefix can ever match.

Verified: grep -o '1millionnight[a-z-]*' index.html returns 1millionnight…; ls css/ | grep millionnight returns only onemillionnight-profile.css.

Structural and accessibility defects

  • 186 <h1> elements (verified count) — one per product. The document outline is meaningless for screen readers and SEO.
  • 188 <img src=""> (verified) — one per product review form. Invalid HTML; browsers resolve the empty URL against the document and can re-request the 3.8 MB page.
  • ~77,000 DOM nodes with no virtualisation — all 185 products are in the DOM at once.
  • i18n re-translates the whole document on every DOM mutation. js/i18n.js:2013 observes document.body subtree and re-walks every text node against a 1,512-entry dictionary after each change — the single largest recurring main-thread cost.
  • Arabic is advertised but absent. ["en","fr","ar"] is declared, but only an EN→FR dictionary (1,421 keys) exists. No dir="rtl" anywhere.
  • Three incompatible theme vocabularies — JS writes body.theme-dark/cream/light (11 CSS rules total) while the real styling keys on html[data-theme="light"] (634 rules).
  • Dead parallax engine — script.js:5216 performs 275 querySelector calls on every load, then :5259 empties the result array. Pure waste.
  • Three parallel catalogue representations merged at runtime (script.js:415-470): 185 HTML sections, 752-entry JSON, 227-entry JS class.

4. Data integrity

The AI Scent Profiler can only see 80 of your 185 products Critical

js/ai-fragrance-finder.js:168-174 filters the 752-entry catalogue against the literal HTML .product-name text using order-sensitive, diacritic-sensitive matching. Result: 106 of 185 products (57%) can never be recommended by the feature you market as "AI".

Affected include Aventus Absolu, Oud Precieux, Hypnotic Amber, Golden Oud, Arabian Oud, Mysterious Oud, Heavenly Oud, Musk Rose, Tabac Royal, Assad Elixir.

The products database table is a dead store High

server.js issues zero queries against products — no SELECT, INSERT or UPDATE. The 153 rows were seeded once and never read. Only 2 of 153 product IDs match anything in the HTML (Layton, Pegasus). The live catalogue comes entirely from index.html and js/fragrance-catalog-data.js.

The words "charme" and "perfume" appear zero times. Every AI coding session in this repo loads 20 KB of instructions for a different product — a plausible driver of the .superdesign/ directory being committed and of the artifact sprawl.

Version control hazards

  • Orphan branch. gh-pages-fresh and v2/main share a root commit with no common ancestor to main. The v2 remote points at the same URL as origin, so git merge v2/main looks safe ("1 ahead, 153 behind") but merges a disjoint history.
  • gh-pages branch is dead code. Pages deploys from the Actions artifact, not the branch. It is 129 commits behind and read by nothing.
  • Manual cache-busting is already wrong. 14 assets carry 9 different ?v= strings; css/fragrance-layout-normalize.css?v=20260850 is not a valid date. One commit (fe4dbdb) exists purely to fix a previous bump that failed in production.
  • Gitignored files are still tracked. .playwright-mcp/ (498 MiB) and .superdesign/ are in .gitignore yet committed — ignore rules don't apply to tracked files.
  • 151 MiB of loose objects never packed; git gc is overdue.
  • opencode.json contains a Raspberry Pi facial-recognition project's ignore list and hard-coded C:\Users\cheri\ paths — breaks for your second contributor.

Note on duplicate images Corrected

36 groups of root images are byte-identical (24.7 MiB), confirmed by MD5 — e.g. aventus.png ≡ aventusabsolu.png, fahrenheit.png ≡ terre-dhermes.png, layton.png ≡ mysteriousoud.png.

But this is not a live "wrong bottle image" bug. In every group one copy is referenced and the other is an orphan — the product images actually displayed come from fimgs.net. This is repository bloat, not a customer-facing defect.

Real orphan waste: 155 of 285 root images (65.9 MiB) are referenced by nothing — and the workflow copies all of them into every deploy.
