# Guides → tutorial videos: investigation & plan

*Prepared 2026-10-13. Scope: replace the 16 interactive guides with one tutorial
video per guide, narrated in Tunisian Arabic, tutorial-style cursor, zooms, montage.*

---

## 1. What exists today

`frontend/src/atelier/lib/guidesData.js` defines **16 guides** built from **33
step hooks**:

| id | id | id | id |
|---|---|---|---|
| navigation | search | collection | finder |
| product | cart | account | loyalty |
| console | client-profiles | record-purchase | store-hours |
| news | users | guest-notes | (16 total) |

`Guides.jsx` renders them as **interactive spotlight tours**: a scrim, a
rectangle over the target element (`[data-guide="…"]`), a tooltip parked beside
it, back/next/finish. Admin-gated (a signed-in non-admin gets an explanation).

That structure is an asset: **the steps are already a storyboard** — target
selector, title, description, placement. The video pipeline should consume the
same data rather than re-author it.

---

## 2. Capability verdict: what NOT to use

**The AI video generator is the wrong tool for this, and I would not spend your
credits on it.** Three independent reasons:

1. **It cannot film your site.** Text-to-video invents a plausible-looking UI —
   wrong buttons, garbled text, a fake layout. A tutorial whose screens are
   hallucinated is worse than no tutorial.
2. **It cannot speak Tunisian.** The audio is generic; there is no dialect
   control, so "real and fluent Tunisian" is not reachable this way.
3. **Cost is absurd.** A 5 s clip is 50–100 credits. A 60 s tutorial ≈ 600–1,200
   credits; 16 guides ≈ **10,000–19,000 credits** — for footage that fails (1).

Everything below costs **zero model credits**: it is screen capture, speech
synthesis and ffmpeg, all local.

## 3. Verified toolchain (measured, not assumed)

| Piece | Status | Evidence |
|---|---|---|
| ffmpeg / ffprobe | **8.1.1 full build** | `ffmpeg -version` — libass, loudnorm, x264 all present |
| French neural voice | **`fr-FR-DeniseNeural`** via `edge-tts 7.3.1` | keyless; 43.4 s rendered over 7 beats |
| Browser render | Playwright + `chrome-headless-shell` 1243 | `page.screenshot()` per frame |
| Frame capture | **1920×1080 JPEG q96**, ~150 ms/frame | 1419 frames in 3 m 08 s |

`edge-tts` is free and keyless (it uses the Edge read-aloud endpoint). To use a
human voice instead, drop a WAV/MP3 per beat into `audio/` and re-run
`build.py` — nothing else changes.

**Dead ends, recorded so nobody re-walks them.** `ffmpeg`'s `crop` filter
evaluates `w`/`h` **once**, at graph-configure time, and never again — measured:
a 2-second clip with `crop=w='1000+1000*min(1,n/25)'` returns width 1000 on all
50 frames. It does re-evaluate `x`/`y` per frame. `zoompan` *does* animate, but
its resampler is fixed: 24–48 dB against an exact crop+lanczos, where a
per-frame `scale` + fixed-size `crop` scores **90 dB** (visually identical). And
Playwright's built-in video recorder is VP8 at a fixed ~600 kbit/s — 0.16
bits/pixel at 1440p — which is why the first two cuts looked soft.

## 4. The pipeline

Three stages, one source of truth (`script.json`), no camera work in ffmpeg.

### Stage A — `script.json` (the storyboard)
One entry per beat: the French line, which selectors to **highlight**
(`spotFrom`), how tight the camera may go (`pad`, `zmax`, `minFrame`), where the
cursor points, and whether the beat clicks. The admin films all start at the
React app's home (`/app`), not inside the console: each walks the same route —
account icon → Admin → the named tab — before the topic lesson begins. The shared
intro is generated by `add-intro.py` from `script.pre-intro.json`; `clickAtEnd`
places navigation clicks relative to the end of the spoken line, and the
`pageFadeIn` / `pageFadeOut` pair hides route changes cleanly. `narrate.py` reads
the lines, `render.cjs` reads everything else — so narration and camera cannot
drift apart.

### Stage B — voice (`narrate.py`)
One MP3 per beat, so a re-take of a single line never re-renders a whole video.
Durations go to `voice.json`, and **the video is sized to the voice**, not the
other way round.

### Stage C — render (`render.cjs`) — deterministic, frame by frame
Nothing is filmed. Every frame is composed on purpose:

- **The camera is a CSS transform on `#root`.** Chromium re-rasterises text at
  the zoomed size, so a 2× push-in is genuinely sharp rather than a 2× upscale
  of a soft source. This is the single biggest quality win in the pipeline.
- **Every value is a closed-form function of the frame number** — camera,
  cursor, spotlight, click ripple. The motion is exactly as smooth as the maths
  and cannot drift or jitter. Measured motion profile of a push-in: 0.3 → 16.8
  → 0.0 over 34 frames, monotone up, monotone down, no oscillation.
- **The spotlight is a `box-shadow` scrim** cut around the element being
  discussed, so the rest of the page falls away and the eye is led. It is
  positioned through the same camera maths, so the hole stays over its element
  while the camera moves.
- **The cursor** is an injected overlay at constant size, gliding to each target
  and then creeping a few pixels so it is never frozen.
- Camera move is **1.15 s**, then a 4 % creep over the rest of the beat so the
  shot stays alive while the narrator talks.

Cost: ~220 ms/frame → ~3–5 min per guide, one guide at a time.

**Two things a tutorial needs that a tour did not.**

*A tutorial changes the page as it goes.* A click opens a form, a field gets
typed into, a table gets filtered. So the target of each beat is measured **at
the start of that beat**, not once up front — and the camera plan follows the
page. Measuring mid-film needs one care: the camera transform lives on `#root`,
and `getBoundingClientRect()` reports the *transformed* box, so the transform is
dropped for the measurement and the next frame puts it back.

*The page has to be put somewhere before the camera rolls.* Two hooks do this,
both plain action lists (`click` / `fill` / `select` / `check` / `wait` /
`waitFor`):

- `setup` — once, before the first beat. "Open the new-card tab", "filter the
  table down to this one customer".
- `beats[].do` — at the head of a single beat. "Now filter the list to the card
  I just created, so I can point at it."

Plus `typeInto` / `typeAt` / `typeText` / `typeClear`, which type into a field
**off the frame clock** — one character per frame at a known rate — so the
reveal is as steady as everything else in the film. `typeClear` matters: typing
into a field that already holds `4` gives you `44`.

*Navigation must be taught from the front door.* The new `pageFadeIn` /
`pageFadeOut` options fade the app surface around a real click, so a route or tab
change is not a hard cut from the old page into the new one. `clickAtEnd` is
resolved only after the voice is synthesised, and lets the click land just after
the instruction even if its wording changes.

Native `window.confirm()` dialogs (delete, redeem, ban) are browser chrome, not
page content, so they cannot be filmed either way. The renderer accepts them and
the film shows the *consequence* instead.

### Stage D — assemble (`build.py`)
1. Frames → H.264 CRF 12 (intermediate).
2. **Intro / outro cards** built from a mid-beat frame of the render itself: it
   already carries the spotlight's warm glow over a dimmed page, so blurred it
   becomes a vignette that matches the rest of the film.
3. **Subtitles**: burned-in **ASS** (libass + harfbuzz shapes French accents
   correctly). Bottom-centre, safe-area padded.
4. **Audio**: one `adelay` per line, `amix`, `loudnorm=I=-16:TP=-1.5`, then
   `aresample=48000` (loudnorm runs at 192 kHz) and `apad` to the full length —
   without the pad the mix ends 3 s early and `-shortest` guillotines the outro.
5. **Encode**: H.264 CRF 18, AAC 160 k, `+faststart`, 1920×1080 @ 30 fps.
   Result: 53.3 s, 27 MB, 4.1 Mbit/s.

### Stage E — audit (`audit.py`)
Three checks, because all three of these faults actually shipped during
development and none of them is visible in a still frame:

1. **Motion continuity.** Every rendered value is closed-form, so the picture
   must never jump. It did, twice — see §6.
2. **Brightness spikes**, which catch a spotlight scrim blinking off between
   beats.
3. **Audio sync** — `silencedetect` onsets vs the planned line starts.

Measured on the **rendered frames, not the encoded file**: H.264 rate control
shifts luma for a few frames after a hard cut and looks exactly like a flash.
Two frames that should be identical measure `PSNR inf`; the encoded file
measured a luma delta of 9.6 at the same instant. Current result: no motion
breaks, no brightness spikes, all 7 lines within 0.24 s.

### Stage F — delivery
- `_recon/guide-video/out/<id>.mp4` — the **masters**, CRF 18, ~110 MB for the
  set. Archive quality; not what a browser is served.
- `out/index.html` — a self-contained gallery generated by `gallery.py` from what
  was **actually produced** (it reads `out/` and `work/`, not `script.json`), so
  a guide that failed to render shows as missing rather than quietly listed.
  Posters are pulled from the film itself, and each card carries the full
  narration with timings.

### Stage H — publish (`publish.py`)
Turns masters into what the Guides tab serves, in one pass:

- **Re-encodes** each film to `public/media/guides/<id>.mp4` at CRF 24 with mono
  96k audio. Measured against the master: **49.1 dB average PSNR, 41.2 dB worst
  frame** — transparent for dark UI screencast, at **half the bytes**
  (110 MB → 50.6 MB for the set). The masters are left alone.
- **Cuts a poster** (1280×720) from each film's `cardStill` beat, so a card
  never advertises a frame nobody chose.
- **Writes `frontend/src/atelier/lib/guideVideos.js`** — `src`, `poster`,
  `duration` and the chapter list, keyed by film id. Chapter times are beat
  starts from `timeline.json` with the title card's offset applied, so
  `video.currentTime = chapter.t` seeks exactly.

It **refuses to write that data file unless every guide published**, so a
partial run cannot silently drop entries from the tab.

The old spotlight tours are **kept**: the seven shop-floor journeys have no film,
and deleting them would remove working content for nothing. `Guides.jsx` gives a
card the player when a film exists and the tour runner when it does not.

### Stage G — the driver (`make.py`)
`validate → seed → narrate → render → build → audit`, per guide. It insists on
two things:

- It shoots against the **demo instance** (port 3100), never the dev server on
  3000, and warns if you point it elsewhere.
- It **re-seeds the demo database before every guide.** Several guides change
  state on purpose — they add a point, redeem a reward, create a card, ban a
  user — and a guide shot after one of those would open on the wrong numbers.

### Where everything lives

Per-guide, so two guides can never share a file:

```
work/<guideId>/audio/<beat>.mp3     one voice file per beat
work/<guideId>/voice.json           its duration
work/<guideId>/frames/<ts>/*.jpg    one directory per run
work/<guideId>/timeline.json        what the render actually did
work/<guideId>/clips/               intermediates
out/<guideId>.mp4                   the master (CRF 18, archive)
public/media/guides/<id>.mp4        the web copy the app serves (CRF 24)
public/media/guides/<id>.jpg        its poster
frontend/src/atelier/lib/guideVideos.js   generated: src, poster, chapters
```

`validate.cjs` runs before every batch and checks all of `script.json` against
the hooks that exist in the **built bundle** — a bad selector otherwise fails
the shoot an hour in, with 800 frames already on disk.

## 5. Quality gates (automated, per video)

- `validate.cjs` clean before the shoot: every `data-guide` selector in
  `script.json` resolves to a hook that exists in the built bundle, no duplicate
  beat ids, every guide has a title/voice/url/ready, every `cardStill` names a
  real beat
- `audit.py` clean: no motion discontinuity, no brightness spike, every line
  within 0.45 s of its planned start
- resolution exactly 1920×1080 @ 30 fps; render reports zero page errors
- all 12 admin videos start at `/app` and show the real path: account icon →
  Admin → the selected tab; the `/app` home → admin-tab clicks are smoke-tested
  in Chromium before the full batch
- **no live-data strings in frames**: the shoot runs against the demo instance,
  which holds invented people only. A real customer name leaking into a public
  video is the worst failure mode here, and the only reliable guard is that the
  real database is never reachable from the render
- visual spot-check: poster frame + sampled frames per video

## 6. Bugs already paid for (do not reintroduce)

| Symptom | Cause |
|---|---|
| Every cut snapped back 4 % | the camera "creep" was a ramp; it must be a **bump**, 1 at both ends of the beat, or the last frame is tighter than the next beat's first |
| Cursor jumped ~11 px at every cut | same shape of bug: the cursor drifted past its target and snapped back. The cursor should glide to its target and **stop** |
| Page flashed bright for ~2 frames between beats | the scrim faded out at the end of one beat and back in at the next. It may only fade where the neighbouring beat has no spotlight |
| Soft, blocky picture | Playwright's video recorder is VP8 at a fixed ~600 kbit/s. Render frames instead |
| Zoom juddered | ffmpeg `crop` evaluates `w`/`h` once, at configure time, and never again |
| Motion looked fine in the audit but not on screen | the audit was reading the encoded file, not the frames |
| **Every admin guide timed out waiting for `ready`** | the readiness check was `document.querySelector(s).width > 0`. `.width` exists on a `<canvas>` and is `undefined` on a `<div>`. Measure `getBoundingClientRect().width` |
| A field ended up holding `44` | typing appends to what is already there. `typeClear: true` |
| The demo server connected to **production Postgres** | `DOTENV_CONFIG_PATH` is not honoured by this repo's dotenv (17.x). dotenv resolves `.env` from the **working directory** — so the demo server is started *from* `demo/`, which has its own `.env` with no `DATABASE_URL` |
| The page stepped brighter on a single frame at the end of `banned` (admin-users) | a beat crossing the screen/document boundary had **both** fades forced to 0. The fade governs the **scrim**, not the camera — it may only be 0 when the *neighbouring* beat has a spotlight. Caught by the audit as `change 8.39` vs a local median of 0.08 |
| The spotlight swept in at 2.5× on the first screen-space beat (admin-users, the ban dialog) | `cam0` was still the previous beat's *document* camera, and a screen-space spotlight is positioned **through** the camera (`x = (r.x − cam.cx) · cam.z + VW/2`), so the hole was drawn 2.5× too large and slid onto the modal over `MOVE` seconds. Snap `cam0 = toCam` whenever the space changes. The audit does **not** flag this — the sweep is gradual, not a jump |
| The audit named the wrong beat | it reads the **body-only** frames but builds `bounds` in **final** time (offset by the 3 s title card), so every printed `t` is 3 s early — and the `near` filter matches any beat *containing* the timestamp, not just a boundary. Read the number, never the label |
| A `.width` check that works on `<canvas>` and nowhere else | see the `ready` row above: prefer `getBoundingClientRect().width` |
| Chapter labels all truncated mid-clause with `…` | splitting on `". "` misses the common case — a narration line is one sentence, so its only full stop is the last character. Strip trailing punctuation *before* measuring the length |
| A loyalty video jumped from the home nav into the customer page | A real click changes the route between captured beats. Add a closed-form `pageFadeOut` / `pageFadeIn` pair so the click is hidden in a smooth crossfade; keep the spotlight in its own overlay |
| Seeded customer's JWT returned `User no longer exists` | SQLite `AUTOINCREMENT` preserves old IDs, so the first seeded customer is not user 2. For customer-facing films, resolve the fictional user's ID by email through the demo admin API; never assume the seed ID |

## 7. Risks and how they are handled

| Risk | Mitigation |
|---|---|
| TTS prosody sounds synthetic | edge-tts is the ceiling without an API key. The pipeline takes human recordings: drop one `.mp3`/`.wav` per beat into `work/<id>/audio/` and re-run `build.py` — nothing else changes |
| UI changes invalidate a video | the pipeline is a script: re-run to re-render |
| Zooms judder | the camera is a CSS transform, so text is re-rasterised at the zoomed size; every value is closed-form in the frame number |
| **Real customer data filmed** | the shoot runs against a throwaway SQLite instance on port 3100 seeded with invented people. The live database (619 real cards) is never named, never opened. `make.py` warns if you point it anywhere but the demo origin |
| A guide is non-reproducible | the demo database is re-seeded before every guide, so a guide that mutates state cannot poison the next run |
| Big files | masters are CRF 18 (≈3.5 Mbit/s); the **served** copies are CRF 24 + mono 96k, 50.6 MB for all 13 — measured transparent (49.1 dB mean / 41.2 dB worst PSNR). `preload="metadata"`, and posters are separate files so a grid of 20 cards loads no video at all |

## 8. Phasing

- **Phase 0 — pilot (1 guide, ~45 s).** ✅ Done, approved after four rounds of
  fixes (quality, French, smooth zoom, spotlight).
- **Phase 1 — infrastructure for a series.** ✅ Done: per-guide work
  directories, `setup` / `do` / typing, per-beat measurement, `validate.cjs`,
  `make.py`, `gallery.py`.
- **Phase 2 — the admin curriculum (13 guides).** ✅ Done, all re-shot from the
  user's confirmed novice path: every film opens on the `/app` home page, pushes
  in on the account icon, opens « Administration et outils » → Admin, arrives at
  the console, then clicks the topic tab — before a single word about the task
  itself. The customer-side `loyalty` film follows the same idea from the top
  menu. Audits clean, chapter data and web encodes published, page verified.
- **Phase 3 — video library.** ✅ The `Guides.jsx` gallery/player and chapter
  navigation are implemented, with the seven unfilmed interactive shop-floor
  tours retained. Web encodes live under `public/media/guides/` (85 MB for the
  set); git ignores `*.mp4`, so only the posters would be tracked without
  `git add -f`. Nothing has been committed or deployed.
